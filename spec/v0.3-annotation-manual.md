**Operational Manual for Observational Annotation of Decision Overhead ($D$) and Intent Deviation ($N$)**

* **Target Audience:** Human Annotators & Research Observers  
* **Version:** 0.3.0  
* **Status:** Operational Pilot Manual  
* **Parent Specifications:** [MF-0.1 (Provisional Core Spec)](MF-0.1.md) | [v0.3 Specification Addendum](v0.3-spec-notes.md)

## 1. Epistemic Hierarchy & Annotator Responsibilities

```
 Raw Evidence ──► Annotator Observation ──► Independent Annotation ──► Reliability Analysis ──► Optional Adjudication
(Logs/Playback)       (Visual Rules)             (Locked Record)          (κ_sub, Gwet's AC1)     (Adjudicated Dataset)
```

> [!IMPORTANT]
> **What You ARE Asked to Do as an Annotator:**
> - Carefully inspect screen recordings, telemetry event streams, and declared task intents ($I_{\text{task}}$).
> - Apply the operational classification rules in this manual consistently to observed screen presentations and user interaction trajectories.
> - Provide concrete evidence snippets (timestamps, prompt text, DOM element descriptions) supporting every non-trivial rating.

> [!CAUTION]
> **What You ARE NOT Asked to Do as an Annotator:**
> - You are **NOT** judging whether a user felt stressed, confused, or cognitively overloaded.
> - You are **NOT** inferring internal psychological causes or mental states.
> - You are **NOT** judging whether the software "caused" a user's behavior.
> - You are **NOT** evaluating whether the Cognitive Entropy theory ($E_c$) is correct or valid.
> - You are **NOT** attempting to guess what another annotator chose or trying to force artificial consensus.

## 2. Declared Task Intent ($I_{\text{task}}$) Protocol

Every task session evaluated in this framework MUST have an explicit, pre-declared statement of user intent called **Declared Task Intent ($I_{\text{task}}$)**.

### 2.1 Creation & Versioning Rules
1. **Who Creates $I_{\text{task}}$:** The task author or experiment coordinator.
2. **When Created:** Strictly **BEFORE** the task session is recorded. $I_{\text{task}}$ may **NEVER** be inferred post-hoc from watching the user's recorded behavior.
3. **Structure of $I_{\text{task}}$:** A clear, tool-independent description of the goal, target artifacts, and explicit constraints.
   - *Example:* "Deploy the static HTML website located in `./dist` to a public URL on Cloud Host X using CLI tool Y, ensuring HTTPS is enabled."
4. **Information Provided to Annotators:** Annotators receive the exact text of $I_{\text{task}}$ before opening the session trace.
5. **Ambiguous Task Intent Protocol:** If $I_{\text{task}}$ is missing, incomplete, or ambiguous, the annotator MUST flag the session metadata as `AMBIGUOUS_TASK_INTENT` and assign `INSUFFICIENT_EVIDENCE` to items dependent on that goal.
6. **User Behavior Inconsistency:** If the user in the video appears to abandon $I_{\text{task}}$ to pursue a different goal, annotators rate actions against the pre-declared $I_{\text{task}}$, marking detours as `INDIRECT_OR_DETOUR_BEHAVIOR` or `TASK_DISCONNECTED_BEHAVIOR`.

## 3. Evidence Access Matrix

Annotators must adhere strictly to information boundary controls during independent annotation:

| Artifact / Information Item | Access Status | Purpose / Rule |
| :--- | :--- | :--- |
| **Declared Task Intent ($I_{\text{task}}$)** | **MANDATORY** | Must be inspected prior to rating. |
| **Screen Video Playback** | **MANDATORY** | Full video playback control (scrub, speed adjustment). |
| **Telemetry Event Log** | **MANDATORY** | Inspect timestamps, app names, window titles, clicks. |
| **Operational Manual / Rubric** | **MANDATORY** | Open-book consultation encouraged during rating. |
| **Other Annotators' Ratings** | **STRICTLY PROHIBITED** | Annotators must NEVER see another annotator's ratings. |

| **Participant Demographics** | **STRICTLY PROHIBITED** | User experience level, age, identity strictly hidden. |

## 4. Decision Overhead ($D$) Rubric

* **Unit of Analysis:** Discrete decision point presented on screen (e.g., modal dialog prompt, dropdown choice, menu pick, configuration form step).
* **Core Question:** *"Was this decision choice directly specified by the pre-declared task intent ($I_{\text{task}}$), or was it presented/required by the digital system during execution?"*

---

### Category 4.1: `INTENT_INTRINSIC`

* **Definition:** A decision point where the choice being made is directly specified by or inherent to the substantive goal defined in $I_{\text{task}}$.
* **Inclusion Criteria:** The options being evaluated directly determine the domain-substantive outcome of the task.
* **Exclusion Criteria:** Choices about software architecture, auth methods, regional hosting, or UI display preferences.
* **Required Evidence:** Screen artifact showing choice options that match parameters explicitly detailed in $I_{\text{task}}$.
* **Common Confounds:** Mistaking tool-required settings for intent choices. If $I_{\text{task}}$ does not specify the choice, it is NOT `INTENT_INTRINSIC`.
* **Borderline Case:** Choosing between "PNG" and "PDF" export. If $I_{\text{task}}$ specified "export as PDF", choosing "PDF" is `INTENT_INTRINSIC`. If $I_{\text{task}}$ just said "export", selecting format is `SYSTEM_PRESENTED`.
* **Concrete Example:** In a budget application, selecting "$5,000" as the quarterly cap when $I_{\text{task}}$ specifies "Set quarterly budget cap to $5,000".
* **Adversarial Example:** Choosing between "US-East-1" and "EU-West-1" in an AWS deploy form. Unless $I_{\text{task}}$ explicitly specified the server region, this choice is `SYSTEM_PRESENTED`, even if the user has a personal preference.

---

### Category 4.2: `SYSTEM_PRESENTED`

* **Definition:** A decision point presented or required by the digital system during execution that is **not** specified by the underlying task objective $I_{\text{task}}$.
* **Inclusion Criteria:** Modal dialogs, dropdown pickers, OAuth selection, permission scope pickers, workspace selection, region selection, confirmation popups.
* **Exclusion Criteria:** Decisions explicitly dictated by $I_{\text{task}}$.
* **Required Evidence:** Screen/log trace showing UI prompt presenting options created by tool engineering.
* **Common Confounds:** Conflating system choices with user intention.
* **Borderline Case:** Interface asks "Save as Draft or Publish?". If $I_{\text{task}}$ specified "Publish article", the draft option is a `SYSTEM_PRESENTED` choice.
* **Concrete Example:** Interface prompts user: "Select Authentication Provider: [Google | GitHub | Email]".
* **Adversarial Example:** Modal popup asks "Do you want to enable automatic telemetry reporting?". Completely system-presented.

---

### Category 4.3: `DUAL_OR_CONTEXT_DEPENDENT`

* **Definition:** A decision point that is system-mediated but serves a legitimate dual role in advancing the task (e.g., authentication required to access a cloud host where authentication itself is necessary, but provider selection is system-structured).
* **Inclusion Criteria:** Necessary workflow gates where software structures how the gate is cleared.
* **Exclusion Criteria:** Pure system artifacts with no task relevance.
* **Required Evidence:** Log trace showing necessary access gate presented with tool-structured options.
* **Common Confounds:** Using this category as a cop-out for ambiguous cases. Use only when both intent necessity and system structuring are present.
* **Concrete Example:** Selecting between SSH Key pair vs Password auth when connecting to a remote server specified in $I_{\text{task}}$.

---

### Category 4.4: `INSUFFICIENT_EVIDENCE`

* **Definition:** Screen recording or log trace lacks context to determine whether the decision was specified by $I_{\text{task}}$ or presented by the system.
* **Inclusion Criteria:** Truncated video, missing prompt text, blurred UI elements, missing $I_{\text{task}}$ metadata.
* **Exclusion Criteria:** Clear visual evidence.

## 5. Intent Deviation ($N$) Rubric

* **Units of Analysis under Investigation:**
  - **Event Level:** Individual log events (single click, window focus tick).
  - **Action Level:** Meaningful user operations (filling form input, submitting modal).
  - **Episode Level:** Temporally connected action sequences representing a behavioral trajectory (e.g., 45-second documentation search episode).

* **Core Question:** *"Does this observed action or episode directly advance the linear trajectory toward $I_{\text{task}}$, or does it represent an indirect detour or disconnected focus?"*

---

### Category 5.1: `DIRECT_INTENT_PROGRESSION`

* **Definition:** Observed action or episode directly advances the declared linear path toward $I_{\text{task}}$.
* **Inclusion Criteria:** Straightforward execution actions (typing code in target file, entering form parameters specified in $I_{\text{task}}$).
* **Exclusion Criteria:** Backtracking, opening help tabs, searching documentation, retrying failed actions.
* **Required Evidence:** Trace shows continuous forward progress without navigation detours.
* **Concrete Example:** User opens target terminal, types `git push origin main`, and hits enter.

---

### Category 5.2: `INDIRECT_OR_DETOUR_BEHAVIOR`

* **Definition:** Observed action or episode deviates from the direct path (e.g., opening help documentation, opening search, menu backtracking, error recovery, UI control search).
* **Inclusion Criteria:** Documentation lookups, searching for hidden controls, menu exploration, fixing typos, retrying failed auth, handling system popups.
* **Exclusion Criteria:** Actions directly advancing intent or domain switches.
* **Required Evidence:** Visual trace showing navigation away from primary workspace to documentation, search bars, or error dialogs.
* **Common Confounds:** Assuming documentation lookup means user was confused. The label records the *observed trajectory detour*, regardless of whether the user was learning, verifying, or confused.
* **Concrete Example:** User opens browser tab, searches "AWS S3 bucket policy syntax", reads page for 40 seconds, then returns to terminal.

---

### Category 5.3: `TASK_DISCONNECTED_BEHAVIOR`

* **Definition:** Observed action or episode switches focus to applications or web domains completely outside the declared task ontology.
* **Inclusion Criteria:** Switching window focus to personal email, social media, sports news, or music applications.
* **Exclusion Criteria:** Work-related documentation or task applications.
* **Required Evidence:** OS window focus log or video showing non-task application active.
* **Concrete Example:** User switches to Spotify window to change playlist during a build process.

---

### Category 5.4: `INSUFFICIENT_EVIDENCE`

* **Definition:** Interaction trace lacks sufficient visual or log context to establish trajectory status.
* **Inclusion Criteria:** 45-second idle gap with no input events and static screen recording; video freeze.

## 6. Borderline-Case Library

This section documents 12 complex edge cases to ensure consistent classification across annotators:

### Case 1: Documentation Lookup
- **Scenario:** User opens a documentation tab to look up CLI command flags.
- **Classification:** `INDIRECT_OR_DETOUR_BEHAVIOR`
- **Why Difficult:** Documentation advances the user's knowledge, but deviates from the direct execution trajectory of $I_{\text{task}}$.
- **Resolving Evidence:** Browser navigation to external doc domain.

### Case 2: Searching for a UI Control
- **Scenario:** User clicks through 3 nested dropdown menus looking for the "Export" button.
- **Classification:** `INDIRECT_OR_DETOUR_BEHAVIOR`
- **Why Difficult:** Navigating menus is part of using software, but menu hunting is a trajectory detour.
- **Resolving Evidence:** Backtracking clicks across non-target menu items.

### Case 3: Authentication Prompt (OAuth / 2FA)
- **Scenario:** User is blocked by an unexpected 2FA prompt while attempting to deploy.
- **Classification ($D$):** `SYSTEM_PRESENTED` | **Classification ($N$):** `INDIRECT_OR_DETOUR_BEHAVIOR`
- **Why Difficult:** Authentication is necessary for security, but the 2FA prompt is a system-presented gate that interrupts the execution trajectory.

### Case 4: Error Recovery
- **Scenario:** CLI throws `permission denied`; user runs `chmod +x script.sh` and retries.
- **Classification ($N$):** `INDIRECT_OR_DETOUR_BEHAVIOR`
- **Why Difficult:** Fixing permissions is required to succeed, but fixing an error is a detour from the primary intent.

### Case 5: Backtracking in Form Wizard
- **Scenario:** User reaches Step 3 of a setup wizard, clicks "Back" to Step 1 to change a setting.
- **Classification ($N$):** `INDIRECT_OR_DETOUR_BEHAVIOR`
- **Why Difficult:** Changing a setting is voluntary, but reversing wizard steps is a non-linear trajectory detour.

### Case 6: Configuration Choices (Region / VPC / Instance Size)
- **Scenario:** Form presents "Instance Size: [t3.micro | t3.small | t3.medium]".
- **Classification ($D$):** `SYSTEM_PRESENTED` (unless $I_{\text{task}}$ explicitly specified "t3.micro").

### Case 7: User Exploration & Discovery
- **Scenario:** User opens an "Advanced Settings" tab, looks at options for 10s, closes tab without changing anything.
- **Classification ($N$):** `INDIRECT_OR_DETOUR_BEHAVIOR`

### Case 8: Learning Behavior / Tutorial Watching
- **Scenario:** User pauses task to watch a 2-minute video on how to configure CORS.
- **Classification ($N$):** `INDIRECT_OR_DETOUR_BEHAVIOR`

### Case 9: Legitimate Multi-Step Workflows
- **Scenario:** $I_{\text{task}}$ specifies "Build Docker image and push to ECR". User runs `docker build`, then `docker push`.
- **Classification ($N$):** `DIRECT_INTENT_PROGRESSION` (Both steps explicitly required by $I_{\text{task}}$).

### Case 10: Idle Periods & Micro-Pauses
- **Scenario:** Screen static for 15 seconds while user stares at code.
- **Classification ($N$):** `DIRECT_INTENT_PROGRESSION` (if dwell time $< 30\text{s}$ during active coding); `INSUFFICIENT_EVIDENCE` (if $> 30\text{s}$ without input or context).

### Case 11: Ambiguous Task Intent
- **Scenario:** $I_{\text{task}}$ states "Set up project", but doesn't specify tools or parameters.
- **Classification ($D$ & $N$):** `INSUFFICIENT_EVIDENCE` (Flag session as `AMBIGUOUS_TASK_INTENT`).

### Case 12: Dual-Purpose Actions (Simultaneous Progression & Detour)
- **Scenario:** User runs `git status` to verify current branch before committing.
- **Classification ($N$):** `DIRECT_INTENT_PROGRESSION` (Checking status is standard linear verification in git workflows).
